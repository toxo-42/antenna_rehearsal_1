# 대회용 프롬프트 사용법

코드는 가져가지 않는다. 이 폴더의 글과 `data/`의 실측 파일만 가져가 빈 폴더에서 만든다. 기존 저장소는 참조하지 않는다.
기준은 교수님의 `antenna_assistant`(Tkinter 앱)이다. 판정 규칙과 카드는 그 프로그램을 따르고, 측정 장비는 SAA-2(HW V2_2)다. 차이와 근거는 `notes/rehearsal_1.md`에 있다.
**리허설 1에서 p0~p9를 모두 돌렸다(2026-11-22).** p5(로컬 LLM), p6(SAA-2 USB, 실물 측정 포함), p7(전후 비교), p8(시연 모드, 외부 공개 없이), p9(안정화)에서 나온 수정은 프롬프트에 반영했다. 2026-11-23에 길이 입력, 사이드바 화면, 관리, 판정 기준, 질문 거절 조건을 더했고, 화면 프롬프트를 `p4_frontend.md`(p4-A)와 `p4b_screens.md`(p4-B)로 나눴다. **이 상태의 프롬프트로 처음부터 다시 돌려 보지는 않았다.**

## 순서
1. 빈 폴더에 `CLAUDE.template.md` 내용을 `CLAUDE.md`로 저장하고, `data/`의 파일을 `tests/data/`로 복사
2. `p0` → `p1` → `p2` → `p3` 순서로 한 세션에 하나씩. 동시에 여는 세션은 최대 2개: `p4_frontend.md`(p4-A)는 p2 무렵부터 git worktree에서 병렬
3. p3과 p4-A를 합친 뒤 `p6` → `p4b` → `p5` → `p7` → `p8` → `p9`
4. 막히면 `recovery.md`

## 대회 시간표
개발 시간은 세 구간, 합쳐서 약 13.5시간이다. 괄호는 배정 시간이고 검토와 수정이 들어 있다.

| 구간 | 단계 | 이 구간이 끝날 때 있어야 하는 것 |
|---|---|---|
| 11-26 14:30~18:00 | p0(20) → p1(50) → p2(40) → p3(30), p4-A(60)는 p2부터 병렬. 17:30부터 합치고 화면 확인 | 합성 샘플을 고르면 그래프와 판정 카드가 뜨는 화면. 19:00~22:00 중간 점검에서 보여 준다 |
| 11-26 22:00~24:00 | p6(60) → p4b(40) | 실물 VNA 측정이 저장됨, 관리와 판정 기준 |
| 11-27 00:00~08:00 | p5(75) → p7(40) → p8(60) → p9(60), 그 뒤 사람 확인, 시연 준비, 발표자료 | 08:00~09:00 제출: 시연 링크, 발표자료, 소스코드 |

- 첫 구간에는 여유가 거의 없다. 리허설 1에서 p0~p3이 약 2시간 35분, p4가 약 45분 걸렸고 그 뒤로 범위가 늘었다. 17:15에 p4-A가 안 끝났으면 `p4_frontend.md` 끝의 줄이기 문장을 쓴다
- 셋째 구간은 8시간 연속이다. 사용량 5시간 창이 중간에 바뀐다. 한도에 가까워지면 무거운 단계(p5)를 시작하지 말고 사람 확인과 발표자료를 먼저 한 뒤, 창이 새로 열리면 이어 간다
- 리허설 1의 실제 시간: p5 약 36분(보정 별도), p6 약 20분, p7 약 18분, p8 약 32분, p9 약 14분. 배정이 남으면 뒤 단계를 당긴다

## 공통 규칙
- 프롬프트 1개 = 새 세션 1개. 끝나면 통과 검사 → `reviewer` 에이전트로 그 프롬프트 대비 누락 검토 → 수정 → `/core-kit:commit` → `/clear`
- 프롬프트는 커밋을 지시하지 않는다. 커밋은 검토 뒤 한 번만 한다 (`/core-kit:commit all`이면 스테이징까지 한 번에)
- 모든 단계의 통과 검사에 `uv run ruff check .`와 `uv run ruff format --check .` 통과가 포함된다
- 검토할 때 reviewer에게 "규칙을 하나씩 틀리게 바꿔도 테스트가 통과하는 곳"을 찾게 한다. 기대값 표가 통과해도 경계와 순서는 고정되지 않을 수 있다
- p1, p2, p6은 reviewer 뒤에 `/core-kit:second-opinion`도 돌린다(직접 입력해야 실행된다. 모델에게 시키면 못 돌린다). 판정 규칙과 USB 통신은 틀리면 뒤 단계가 전부 틀린다
- 통과 검사의 **기대값을 고쳐서 통과시키지 않는다.** 기대값이 이상하면 멈추고 사람이 판단한다
- 같은 문제로 2번 실패하면 `recovery.md`의 R1
- 모델: 구현 세션은 Opus(p0이 만드는 `.claude/settings.json`으로 고정). 명세 검토, `second-opinion` 결과 판단, 설계가 흔들릴 때만 `/model fable`로 올렸다가 되돌린다

## 차후 확장 (대회 범위 밖)
대회에서는 LLM이 카드를 풀어 쓰고(p5-A), 질문에 맞는 설명 번호를 고른다(p5-B). 아래는 그 뒤에 붙일 수 있는 것이고, 어느 것도 "숫자·방향·결론은 코드가 만든다"는 원칙을 바꾸지 않는다.
- 설계 가이드 문서(35단원) 검색: 고른 설명에 관련 단원을 **원문 그대로** 함께 보여 준다
- 조정량을 mm로: 현재 도체 길이를 입력받아 %를 길이로 바꾼다
- PC에서 하는 OSL 교정: USB 값은 교정 전 값이다. 교정 키트(Open, Short, Load)가 있으면 교수님 프로그램의 `calibration.py` 방식으로 붙인다
- `QuestionRouter` Protocol 뒤에 구현을 추가하는 방식으로 붙인다. 판정 코어(p1·p2)는 건드리지 않는다
